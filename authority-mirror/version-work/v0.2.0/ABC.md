## 1. 目标

让 DM 不受内置参考单位覆盖率限制，能够从单位模板准备一场遭遇，并以明确的“第 0 回合”完成棋子摆放与初始状态设置；只有 DM 确认遭遇后，才投先攻并进入既有的第 1 回合战斗流程。

目标流程：

```text
自定义或复制单位模板
→ 加入遭遇
→ 第 0 回合摆放并设定初始状态
→ DM 确认遭遇
→ 投先攻 / 处理既有平局裁定
→ 进入既有战斗流程
→ 战斗中投入预备单位或临时加载单位
→ 在场 / 临时离场 / 再入场 / 结束参战
→ 结束战斗，选择保存记录与清理战场
```

## 2. A——拟实施范围

仅在用户批准本 ABC 后，允许在产品 Workspace 实施以下最小闭环。

### A-1 自定义单位模板库

- 建立与现有参考单位并列、但来源可辨识的自定义单位模板管理能力：新建、编辑、复制、归档；归档模板不再用于新遭遇，但不破坏引用它的历史遭遇或战斗。
- 模板最小字段为：名称、阵营/关系提示、体型、AC、HP、速度、占位、动作、资源、备注。
- 每个模板必须标记来源类型：参考模板（`reference`）、自定义模板（`custom`）或变体模板（`variant`）；`variant` 必须保存其来源模板 ID 与创建时的基线修订号（`revision`，如存在）。
- 允许设置基础棋子表现：默认显示名、简称和颜色。它们是表现/准备默认值，不是规则结论。
- 不以资料来源区或模型常识自动填充字段；DM 可手工录入。对 `reference` 的任何既有数值正确性仍保持既有的 `unknown` 边界，除非另有逐字段规则核验记录。

### A-2 模板、准备数据与战斗实例隔离

- `UnitTemplate` 是长期库数据；遭遇中的成员记录必须在加入时保存模板引用与所需的不可变快照；正式开战时据此创建独立 `CombatantInstance`。
- 已创建的战斗实例持有自身 HP、状态、资源、位置、朝向和发射口；后续模板编辑、归档或删除候选不得改变它。
- 准备阶段的初始 HP、名称、朝向、发射口、位置和状态只能写入遭遇准备成员/最终实例，绝不回写模板。
- 战斗中产生的 HP、状态、资源与行动经济变更不得写回模板或遭遇默认值；既有事件日志（`Event Log`）、补偿式撤销、快照（`Snapshot`）和自动保存语义保持不变。

### A-3 遭遇草案与第 0 回合

- 提供遭遇草案的新建、命名、保存、恢复、继续编辑与删除/放弃入口；单次仅允许一个活动遭遇进入现有单一 `CombatSession`，不扩展多战役或跨设备同步。
- DM 可从单位库向遭遇添加同一模板的多个成员；每个成员在第 0 回合可独立调整显示名、初始 HP、位置、朝向、发射口和初始状态。
- 第 0 回合必须显式标记为 `preparation`，没有先攻顺序、当前行动者、行动经济消耗或自动回合推进；它不是第 1 回合，也不产生伪造的骰子结果。
- 未确认前，DM 可保存、退出、恢复并继续编辑准备状态；恢复后不得丢失模板快照、成员配置或地图摆放。
- DM 的“确认遭遇”操作必须显式、可审计地将准备状态冻结为战斗初始状态；确认后才启用既有投先攻、平局裁定与第一回合开始路径。
- 已确认/已开始的遭遇不得回到可随意编辑的第 0 回合；若需要调整，则仅能沿用既有 DM 人工修正与补偿事件语义，或创建新的遭遇草案。

### A-4 兼容接入与最小验证

- 保持 `CombatSession` 单一权威状态、跨标签页共享、JSON 导入导出与本地自动保存；不为遭遇准备建立可与战斗状态相互覆盖的第二份会话。
- 为准备状态、模板快照、确认边界和导入版本增加明确的 Schema 版本与校验。无法迁移或不支持的导入必须安全拒绝且不覆盖当前数据。
- 为模板/实例隔离、准备保存恢复、确认前禁止投先攻、确认后既有先攻进入，以及补偿事件不改写旧事件建立自动测试和浏览器工作流验收。

### A-5 战斗中加入、离场与重复再入场（修订待批准）

- 第 0 回合允许把遭遇成员标记为“场外预备”（`reserve`）。预备单位保存名称、关系、HP、资源、状态与模板快照，但未投入时不摆放棋子、不进入有效先攻序列、不获得当前行动者身份。
- 已开始战斗期间，DM 可以从单位库或角色栏临时加载一个单位。加入前必须在确认页设置显示名、关系、当前 HP、资源、初始状态、入场位置和先攻；确认前只是 `EntryDraft`，不得冒充参战实例或写入战斗统计。
- 场外预备首次投入时物化战斗实例；临时加载确认时按当时模板快照创建新的 `CombatantInstance`。两者入场后走同一套事件、先攻和自动保存边界。
- 首次入场由 DM 选择“现场投先攻”或“手动填写先攻”。现场投骰的最终值为 `1d20 + 先攻调整值`；参考怪物默认读取已准入条目中的显式先攻调整值，自定义/变体模板保存 DM 默认值，投入表单仍允许逐项覆写。手动填写的是最终先攻，不再重复叠加调整值。若该先攻位置在当前轮尚未经过，本轮可行动；若已经过，则下一轮首次行动。同值顺序仍由 DM 裁定，入场不授予额外行动。
- 已参战实例支持“临时离场”与“结束参战”两种明确操作。临时离场会从地图和当前有效先攻序列移除，保留同一实例的当前 HP、已消耗资源、法术位、原先攻、实例 ID 和历史；离场时立即清除临时 HP、手工状态、Buff、Debuff 与该实例维持的专注效果。结束参战则默认不再进入本场先攻，但仍保留记录。
- 同一实例可在一场战斗中多次执行“在场 → 临时离场 → 再入场”，不得因再入场复制为新实例。再入场时 DM 重新选择位置，默认沿用原先攻，也可明确修改；当轮可行动性仍按“先攻位置是否已经过”判定。
- 再入场不恢复离场时已经清除的临时效果；保留当前 HP、已消耗后的资源与法术位。HP 为 `0` 的实例不得再次入场并恢复正常行动。D2-015 仅为怪物/NPC 增加独立于临时离场的最小死亡记录、尸体棋子与 DM 手动处理；角色死亡豁免状态机仍延期至 `BL-020`。
- 离场期间不自动结算伤害或治疗；如需调整，由 DM 在再入场确认前手工处理。由于 Buff、Debuff 与专注已在离场时清除，不存在继续倒计时后自动恢复的问题。首版不实现自动增援触发或场外规则引擎。
- 加入、临时离场、再入场、重置临时效果和结束参战都必须追加顺序事件；撤销只能追加补偿事件。当前行动者离场时必须安全跳到下一个仍在场且可行动的实例，不得卡死回合。

### A-6 战斗结束、记录去留与战场清理（修订待批准）

- DM 结束战斗前，界面必须汇总并显示：在场参战实例、临时离场实例、从未投入的预备单位，以及未确认的临时加入草稿的数量和处置后果。
- 确认结束后，所有已参战的在场和临时离场实例统一标记为本场参战结束，停止先攻和行动并禁止再入场，但保留结束时 HP、资源、状态、位置/离场身份及全部历史。
- 从未投入的预备单位标记为“未使用预备”（`unused reserve`），随遭遇关闭但不伪造为已参战；未确认的 `EntryDraft` 自动放弃，不创建实例、不进入战斗统计或角色回写。
- 结束确认后询问是否保存战斗数据。选择保存必须自动导出完整 JSON；选择不保存必须二级确认“确定不保存？这会使你失去本次战斗数据”，且不产生独立战斗档案。
- 不论是否导出，随后都必须询问“是否清空战场地图”。选择清空时，清除地图棋子、战斗页活动单位和先攻，返回可创建新遭遇的状态；选择保留时，返回战斗页的战后清理模式，允许逐个撤下棋子或“撤下全部敌对单位”，但不允许继续行动、恢复先攻或再入场。
- “不保存但保留地图”只表示不建立独立历史档案；为了完成战后清理，当前活动会话可暂存最终战场。当 DM 清空战场或新建遭遇时，该未归档记录才被明确丢弃。
- 结束战斗不自动回写角色长期 HP、HP 上限、资源、永久 Buff 或 Debuff。长期角色结算仍属于 `BL-019`，不得用一个笼统的“审核回写”把临时伤害变成永久 HP 损失。

## 6. 数据边界与状态模型

建议在批准后采用以下单向关系，具体字段和实现位置由 `IMPLEMENTATION.md` 记录：

```text
UnitTemplate（长期保存、带修订号）
  → EncounterMember（模板引用 + 不可变快照 + 准备阶段覆写）
  → 确认遭遇（可审计边界）
  → CombatantInstance（仅在本场战斗内可变）
      ↔ presenceStatus（on-field / temporarily-away，同一实例可往返）
      → participationStatus（active / ended，结束后不可回场）
      → lifeStatus（alive / dead / transformed；死亡不等同于临时离场）
  → 只追加的 CombatEvent + Snapshot

战斗中临时加载：
UnitTemplate / 角色预设 → EntryDraft（未确认） → 确认后新 CombatantInstance
```

数据责任：

| 对象 | 负责保存 | 不得保存或修改 |
|---|---|---|
| `UnitTemplate` | 可复用默认字段、来源标记、修订号、归档状态 | 单场 HP、位置、状态、资源消耗、行动轮 |
| `EncounterDraft` / `EncounterMember` | 第 0 回合成员、模板快照、开战前覆写与准备状态 | 已开始战斗的可变事实、长期模板的反向修改 |
| `EntryDraft` | 临时加载的未确认表单值与来源快照 | 参战身份、战斗统计、长期数据回写 |
| `CombatantInstance` | 已确认后的单场 HP、资源、状态、位置、朝向、发射口、先攻、在场/参战/生命状态，以及死亡/转化来源记录 | 模板/遭遇默认值的回写；再入场时复制新实例；将角色死亡豁免冒充为怪物死亡记录 |
| `CombatEvent` / Snapshot | 确认后战斗变更与可恢复性 | 未确认 UI 草稿；旧事件的改写或删除 |

`reference`、`custom`、`variant` 是模板来源标签，不是权利或规则正确性结论。任何规则资料字段仍遵守本地私有验证与 `unknown` 权利边界。

## 7. 兼容性与迁移

- v0.1.0 的归档包与静态身份不改动；迁移工作只面向产品 Workspace 中未来 v0.2.0 的运行数据和用户导出文件。
- 旧导入数据必须先保留原始字节/文件，再执行显式、可报告的 Schema 迁移；迁移失败、未来版本、损坏或不完整数据必须拒绝导入且不覆盖现有会话。
- 旧 `CombatSession` 若没有遭遇准备字段，应被识别为既有战斗会话，不倒推或伪造第 0 回合历史。
- 新格式导出必须包含 Schema 版本、模板修订号/快照、遭遇准备或确认状态，以及既有事件日志/快照完整性信息。
- 迁移/导入不得让模板后改影响旧导入会话；回退方案是保留原导出并恢复至迁移前可读数据，而不是静默降级或删除。
- 缺少新在场/参战字段的已开始旧会话，迁移时默认现有战斗实例为 `on-field + active`；已结束会话默认为 `participationStatus: ended`。不得倒推临时离场、场外预备或临时加载历史。
- 缺少 `lifeStatus` 的旧会话实例默认迁移为 `alive`，即使旧数据的 HP 已为 `0` 也不得静默倒推为死亡；DM 必须在新会话中明确处理，避免伪造死亡历史。
- 新 JSON 必须区分在场实例、临时离场实例、已结束参战实例与未使用预备；未确认 `EntryDraft` 不得被导出为已参战对象。

## 8. 验收标准

3. 模板修改或归档不改变已保存遭遇的模板快照，也不改变已开始战斗的实例；

5. 第 0 回合可保存、刷新恢复、重新打开并继续编辑；地图摆放、朝向、发射口、初始 HP/状态和成员显示名均保留；
6. 只有 DM 明确确认遭遇后，才创建/激活战斗初始状态并进入既有投先攻、平局裁定和第一回合流程；
7. 确认后的战斗继续使用单一 `CombatSession`、补偿式撤销、顺序事件日志、快照、自动保存和 JSON 导入导出，未产生第二份互相覆盖的会话状态；
8. 战斗中的 HP、资源、状态、位置、朝向和发射口不写回模板或准备默认值；
9. 至少覆盖模板/实例隔离、确认边界、保存恢复、导入迁移/安全拒绝与事件不变性的自动测试；浏览器流程有真实执行记录；

| 死亡记录被误解为完整复活/死亡规则引擎 | UI 明示“DM 手动事件”；规则基线仅准入本地 Markdown 锚点的有限结论；角色状态、即时死亡、稳定和死亡豁免继续留在 BL-020。 |
| 特殊转化覆盖或污染死亡实例 | 旧实例只追加 `transformed` 与目标 ID，新模板物化为独立实例；允许原位置确认或批量摆放，位置冲突必须阻止确认。 |

## 10. 建议的最小实施切片（不构成授权）

1. **数据底座：** 带修订号的 `UnitTemplate`、来源标签、遭遇草案/成员、明确的 `preparation → confirmed` 状态和 v0.1.0 导入迁移。
2. **DM 准备界面：** 模板新建/复制/编辑/归档；将模板多次加入遭遇；第 0 回合地图摆放与最小初始覆写；保存恢复。
3. **确认接桥：** 审计化确认，生成独立战斗实例（`CombatantInstance`），并复用既有先攻/平局/第一回合路径；禁止逆向编辑。
4. **参战生命周期：** 场外预备、临时加载确认、首次入场先攻、临时离场、结束参战与同实例重复再入场。
5. **战斗收尾：** 四类对象汇总收口，保存/不保存防呆，清场/保留地图选择及只读战后清理。
6. **有限死亡处理：** 怪物/NPC 死亡记录、尸体棋子、DM 特许复起与特殊转化；角色死亡豁免保持延期。
7. **证据收口：** 自动隔离/迁移/参战状态机测试、浏览器工作流、真实 DM 验收；完成后停止并等待独立评审授权。
