## BL-007 美术地图、动态边界与复杂地图编辑器

### 想解决的问题

未来地图不能继续把网格尺寸、可见容器、图片和棋子位置视为同一个 CSS 背景。DM 应先确定逻辑格数与每格距离，再导入地图图片并对齐；跑团过程中还必须能临时向上、下、左、右扩展空白格，而不移动既有棋子、不拉伸底图或破坏位置历史。

v0.7.0 Amendment 01 只候选修复现有空白网格的 `MapViewport / MapCanvas` 越界，不实施本 Backlog 的图片、动态边界、负坐标、资源存储或事件能力。

### 候选数据模型

- 地图至少区分 `baseBounds` 与 `workingBounds`。两者都使用半开区间的有符号边界：`minX / minY / maxXExclusive / maxYExclusive`。
- `baseBounds` 是创建地图和对齐图片时确认的正式范围；`workingBounds` 是当前会话可摆放、可计算范围，可以大于基础范围。
- 默认空白地图仍从内部 `(0,0)` 开始，保持现有位置数据；向上/左扩展只减小 `minY/minX`，向下/右扩展只增大最大边界。既有单位、范围原点和历史位置不得因扩展而批量平移。
- 用户层默认编号保持正数；扩展到原点之前时显示负数编号，零只作为内部原点。显示编号与距离计算必须分离，不能用展示格式改写 Domain 坐标。
- 地图图片作为 `baseBounds` 下方的独立资源层；Session 只保存资源身份/hash、对齐变换、透明度与边界引用，不应把无界 Base64 图片直接塞入 `localStorage`。

### 地图导入流程

1. 先设置列数、行数与每格距离；未确认逻辑格数时不能把图片作为权威地图。
2. 再选择本地图片，进入不会写入战斗事件的对齐预览。
3. 最低支持缩放、偏移、裁切、90°旋转和网格透明度；默认把图片对齐到 `baseBounds`，但最终结果由 DM 确认。
4. 自动网格识别即使以后加入，也只能作为候选提示；不得未经确认改变格数、坐标或棋子位置。
5. 图片加载失败、资源丢失或格式不支持时保留逻辑网格、单位与事件，显示可恢复错误，不能用空图片覆盖资源身份。

### 四向热扩展与视觉合同

- 地图四边提供低干扰的 `+1格 / +5格` 扩展控制；向上和向左是首版必要能力，不得只实现向右和向下。
- 临时扩展区使用与基础地图有区别但不过度醒目的蓝灰底纹或细斜纹；基础边界以虚线/角标标识，地图图片不延展到新增区域。
- 扩展追加 `map.bounds.expanded` 或等价顺序事件，保存方向、数量、前后边界与操作者语义；撤销通过补偿事件恢复，不删除历史。
- 收缩只能作用于最外层连续空白区域；存在棋子、多格占位、待投入位置、范围预览或其他位置引用时必须阻止并指出对象。
- 适应屏幕、战术尺寸、滚动位置和视口中心属于呈现；`workingBounds` 与扩展/收缩属于 Domain 事实，不能保存在 `UiPreferences`。

### 进入实施前必须决定

## BL-009 多人实时同步、账户、权限与房间

### 长期核心方向

单人版浏览器内 `CombatSession` 只能作为当前单 DM Authority。多人版本必须由 DM 主机或服务端持有会话 Authority：客户端提交命令请求，Authority 原子校验操作者权限、会话版本、轮次与目标状态，写入唯一顺序事件，再向各客户端广播对应投影。

- DM 保留最终裁定、强制修正和补偿撤销权。
- 玩家只能为明确授权的角色提交能力范围内的命令，例如移动、骰点、资源使用、目标和范围选择。
- 玩家端读取单独设计的 allowlist `PlayerProjection`，不得直接接收原始 `CombatSession`；DM 暗骰、隐藏单位、隐藏地图、私密笔记和待裁定信息不得泄露。
- 撤销是服务端追加补偿事件；初期只允许撤销最新且没有后续依赖的可逆事件。
- 所有写请求必须考虑身份、版本、幂等键、乱序、重复提交、断线恢复与重连。

### 分阶段链路

1. 只读同步显示：多人看到各自权限允许的相同地图、轮次、单位和事件。
2. 身份、房间、角色归属和 DM/玩家权限。
3. 玩家提交受限命令，由 Authority 接受、拒绝或要求 DM 确认。
4. 断线恢复、重连、幂等、事件顺序、冲突和补偿撤销。

首版不建设完整规则引擎、玩家直接修改战斗事实、无权限自由协作编辑或完整 Campaign 云平台。BL-011、BL-017 与 BL-021 保留各自编号和职责，不合并进本项。

## BL-030 团务记录、快速捕获与确定性报告

### 想解决的问题

结构化 `CombatEvent` 能回答战斗中发生了什么，但不适合承载玩家承诺、线索发现、临时叙事裁定、待办事项和下次开团准备。DM 应能在不打断跑团流程的情况下快速记录这些内容，并在赛后整理为可追溯的战后报告或团后报告。

### 阶段一：团务记录

- 支持 DM 在跑团过程中快速记录自由文本；首版默认仅为本地 DM 私有记录，不引入账户、房间、网络同步或玩家写入。
- 团务记录可以关联 `sessionId`、轮次、`eventId`、角色或地图上下文，但关联只提供定位，不得反向修改 `CombatSession`、`CombatEvent`、`CharacterSheet` 或地图事实。
- 区分未经整理的 Quick Capture 与经 DM 审核的 Canonical Campaign Record；整理、修正或删除笔记不得无痕改写战斗日志。
- 未来如支持共享，必须显式区分 `dm-private` 与 `party-visible`；权限和多人写入依赖 BL-009，多战斗 Campaign 与跨设备身份依赖 BL-017。

### 阶段二：确定性报告

- 战后报告从结构化事件、HP/资源变化、死亡后结果、撤销、人工修正和战后回写结论中生成事实摘要。
- 团后报告组合经 DM 选择的团务记录、战斗摘要和叙事重点；不得把全部事件机械堆叠成不可读流水账。
- 报告内容应保留对应 `eventId`、`noteId` 或其他稳定来源引用，使 DM 能返回原始记录核对。
- 自动生成结果始终是可编辑草稿；只有 DM 明确确认后，才可保存为正式团务记录。
- 报告模板、索引和摘要属于 Derived State，必须可重新生成、可失效且生命周期可追踪；来源变化或删除后，不得继续把旧派生内容展示为当前事实。
- 首个实现不得依赖 AI 或网络服务。确定性报告也是后续 AI 不可用、失败或未授权时的完整回退路径。

### 进入实施前必须决定

- 团务记录是独立于战斗 Session 的长期对象，还是先采用随单场导出包保存的窄实现；不得未经迁移设计扩大现有 `localStorage` Envelope。
- Quick Capture、正式记录与报告草稿的身份、修订、删除、导出和恢复合同。
- 战后报告与团后报告各自包含的事件类别、默认筛选、人工选择和呈现格式。
- 地图上下文使用稳定地图身份还是仅保存当时名称；不能把可能变化的显示名称当作唯一引用。
- 必须通过新的 ABC 冻结数据模型、来源追踪、失败恢复、导出和浏览器验收；本 Backlog 的 Committed Direction 身份不构成版本安排或 Implementation 授权。

## BL-019 候选边界

### 想解决的问题

战斗中的普通 HP 损失、临时 HP、Buff、Debuff 和行动状态默认都属于单场 `CombatantInstance`，不应在“结束战斗”时被一个笼统的回写按钮自动变成长期角色变化。DM 应能逐角色明确选择：

1. `结束战斗，无永久损伤`：长期当前 HP、HP 上限和永久效果保持战前值；
2. `结束战斗，获得永久损伤`：经二级菜单和再次确认，写入永久 HP 上限扣除及一个或多个永久 Debuff；
3. `结束战斗，获得永久奖励`：经二级菜单和再次确认，写入永久 HP 上限增加及一个或多个永久祝福 / Buff。

### 候选数据与交互

- 复用现有独立于 `CombatantInstance`、`UnitTemplate` 和事件日志的长期 `CharacterSheet`，再为永久效果与结算历史建立独立合同；不得改写既有卡片身份与修订边界。
- 永久 Debuff / Buff 至少包含名称、自定义说明、来源战斗、创建时间、状态和可选骰式；解除或修正必须追加补偿记录，不得无痕删除历史。
- 永久 HP 变化和可选效果数值使用可追加骰项的构造器，例如 `[2]d[8] + [1]d[4] + [3]`，标准化为 `2d8+1d4+3`；允许继续添加 `[数量]d[骰面]` 项和末尾固定修正值。
- 每个数值效果必须明确选择求值模式：`roll-once`（获得时掷一次并固定结果）或 `roll-on-trigger`（保留公式，每次在战斗中触发时重新掷骰）。两种模式都保存原始公式；前者保存固定逐骰结果和合计，后者逐次记录触发时间、逐骰结果、合计、应用目标和对应战斗事件。
- 骰式只生成 DM 指定的数值，不自动判断伤势、祝福、规则合法性或效果语义，不扩展为完整规则引擎。
- 战斗数据选择“不保存”时，完整 `CombatSession`、地图和事件日志是否丢弃，与已由 DM 明确确认的长期角色变化必须分开处理；默认候选是丢弃战斗记录但保留长期结算及其最小审计来源。

### 与战斗系统联动

- 长期诅咒 / 祝福保存在 `CharacterSheet.persistentEffects`，角色加入遭遇时只投影为本场 `CombatantInstance` 的只读来源快照；战斗内触发记录不得偷偷反写或改写长期效果定义。
- “战斗”Tab 为当前角色增加“长期效果”区域，始终显示名称、正负类型、骰式、求值模式、固定值或本次可触发状态，以及长期角色卡来源。
- `roll-once` 效果在获得时确定数值；进入后续战斗时沿用同一固定值。例如永久 HP 上限 `-2d8` 在获得时掷出 `-11`，以后每场战斗都按 `-11` 投影，不再重掷。
- `roll-on-trigger` 效果保留类似 `2d8+1d4+3` 的公式；在“战斗”Tab 由 DM 点击“触发并掷骰”，每次产生新的结果和顺序事件。首版不自动判断“每回合”“命中时”或“受伤时”等复杂触发条件。
- 数值必须声明应用方式，候选最小集合为：伤害、治疗、临时 HP、本次掷骰修正、当前战斗资源变化和仅记录数值。HP 上限的永久增减只允许 `roll-once`，避免每次触发重新改写长期角色结构。
- 每次动态触发先显示本次结果和目标，DM 再确认应用；取消则只保留预览、不写事件。确认后追加例如 `persistent-effect.rolled` 与相应战斗变更事件，仍可通过补偿事件撤销本次战斗应用。
- 解除、压制或永久修改诅咒 / 祝福必须回到长期角色卡并经 DM 确认；在战斗 Tab 隐藏或暂时不触发，不等于删除长期效果。

### 进入实施前必须决定

- “无永久损伤”是保持完整战前长期状态，还是允许单独回写当前 HP / 资源；建议默认完整保持战前状态。
- 永久 HP 上限变化是否最低保持为 `1`；建议默认最低为 `1`，任何例外另行二次确认。
- 每个 Debuff / Buff 选择 `roll-once` 或 `roll-on-trigger`；两者都应实现。建议 HP 上限变化只允许 `roll-once`，战斗伤害、治疗、临时 HP、掷骰修正和自定义数值允许两种模式。
- 动态效果的触发频率是否需要自动化；建议首版仅支持 DM 在“战斗”Tab 手动点击触发，自动每回合 / 命中 / 受伤触发延后到有独立规则合同时再决定。
- 选择“不保存战斗”后是否仍保留已确认的长期角色结算；建议保留，否则“永久”无法成立。
- 本项进入任何版本前，必须通过新的或重新批准的 ABC 定义长期角色卡 Schema、迁移、预览、撤销和验收标准；不得附带进入 v0.2.0。

### 复盘后的阶段顺序

3. **后期低优先级：AI 辅助建卡。** 必须等待多 Profile 与 CharacterDraft 审核链稳定；AI 只生成带来源、置信度和缺失项的 Draft，不得补造规则、判断合法性、创建正式角色或覆盖已有修订。

### 想解决的玩家问题

新手不该先被要求理解职业、背景、专长、熟练项、法术位或完整法术表，才能开始创建角色。玩家可以从“我想玩一个优雅、神秘、平时低调、关键时刻很厉害的旅行者”这样的角色幻想开始；系统的职责是帮助他逐步收敛，而不是把几个职业名轮流硬推给他。

玩家应能保存“喜欢 / 不喜欢 / 尚未决定”的偏好，拒绝推荐并继续修正。系统最后才把概念落实为职业、背景、技能、装备、法术等规则字段；任何自动采用的默认项都必须可见、可逐项修改。默认采用最新适用规则，但必须显示规则版本，并允许玩家明确选择旧版或其他来源。

### 预期体验

背景是可选共创，不是强制写作：玩家可以只要规则字段，或选择一句动机、轻量人物关系，或在同意后再扩展完整经历与战役钩子。玩家可以明确说“不想写背景”“太沉重”或“不要家族仇恨”。叙事背景和规则背景效果可分别调整；仅面向 DM 的钩子、禁忌主题和关系摘要必须与玩家卡分开保存，且经玩家同意后才可共享。

施法职业必须有独立流程：以“伤害、控制、防御、治疗、探索、社交”等实际玩法组织推荐，解释玩起来的感觉，并展示专注、准备数量、法术位、已知法术或法术书等关键约束。新手可选预设备法术包，高级玩家仍可细调；不能把完整法术表直接扔给新手。

### 交接到战斗

目标是让自然对话只能生成可拒绝、可修正的 `Character Draft`，再按以下流程进入 Terminal：

```text
Agent 生成 Character Draft
→ Terminal 解析与 Schema 校验
→ 显示导入预览、缺失项、默认项与规则版本
→ 玩家 / DM 确认
→ 写入长期 Character Sheet
→ 生成可进入战斗的 UnitTemplate / CombatantInstance
```

Agent 不能直接改写已有长期角色卡、战斗实例或事件日志；导入失败也不得覆盖已有数据。长期角色卡、战斗实例和事件日志仍分离；战斗结束后的 HP、资源和法术位继续经过 DM 审核回写。每份角色卡需要版本、修订与规则来源状态，不能把模型自然语言当作唯一规则事实。

### Agent 是可选入口

Agent 只负责对话、解释与生成 Draft；Terminal 的手工建卡、JSON 导入和战斗功能不能依赖联网模型。API Key 不得放进浏览器。属性修正、熟练项、法术位、字段完整性与 Schema 校验优先由确定性代码完成；复杂施法、多职业或规则冲突才考虑升级模型能力。

每次调用应可追踪模型、Token、费用和检索的最小规则范围，并支持每角色、每团预算上限和关闭 Agent 模式。不得反复发送完整规则库，也不得在 Terminal 内直接建设大型 RAG、Embedding 或向量数据库。

### 首版不做什么

不包含全量规则引擎、无人审核的“角色绝对合法”承诺、自动裁定复杂法术、多人实时协作、公共开放规则库、自动公开分享角色或背景、向浏览器暴露 API Key，或把 LoreBuddy 全部资料直接嵌入 Terminal。

### 未来首版的接受方向

新手应能自然描述角色幻想、拒绝和修正推荐；完成一个非施法角色与一个施法角色；得到可读简介与结构化草案；在 Terminal 预览、校验、确认并导入；导入后直接创建战斗实例；战斗结束仍走 DM 审核回写。关闭 Agent 后，Terminal 核心功能必须不受影响；成本、模型调用和规则范围必须可追踪。

在其进入新交付前，优先解决可验证角色数据进入战斗的基础能力；对话式建卡、施法向导、成本控制和 Agent Gateway 应作为后续独立范围再经 ABC 批准。

## BL-033 CharacterProfile、AdventureState 与版本化回写

### 来源与优先级

本项整合 BL-016 的版本/迁移问题、BL-018 的角色投影问题和 BL-019 的长期回写问题，但保留三者原编号和业务职责。它是本次复盘唯一明确的高优先级架构候选，应早于新增复杂休息规则、扩展关联单位、多 Profile 导入、AI 建卡和多人角色写入。

### 三层角色状态

```text
CharacterProfile
  身份、等级/构筑、永久资源获取、永久身体/形态、低频历史
        ↓
AdventureState
  当前 HP、已消耗资源、生命骰、消耗品、长休武器精通选择、
  控制期限、跨场景非永久效果与可逆形态
        ↓
CombatantInstance
  单场位置、先攻、行动经济、战斗 HP/资源、效果和事件
```

`CombatProjection` 必须明确引用一个 Profile revision 和一个 AdventureState version；战斗不得直接修改前两者。

### 同一交付必须解决的三个问题

1. **修订膨胀：** 将无限全量 CharacterSheet revisions 改为不可变锚点快照 + 锚点间的类型化、可审计变更；不得采用脆弱的通用 JSON-path 差异链。旧记录保持只读，并通过 copy-on-write 迁移。
2. **战后冲突：** 将当前“revision 已变化就整份过期”升级为 DM 审核的三方合并：战斗开始 Base、战斗结果、当前 AdventureState。每项可选择采用绝对结果、语义安全时应用增量、拒绝，或填写修正值与原因；结构性变化继续人工处理。
3. **高频状态归属：** HP、资源、生命骰、消耗品、休息和跨场景效果只更新 AdventureState，不再为每次消费/恢复制造永久 Profile revision。

### 长休、短休与生命骰的关联阶段

- 在本架构交付中建立“短休、长休、生命骰”入口，作为第一条 AdventureState 验收路径。
- 初期按钮可显示“待配置 / DM 裁定”，记录意图并解释边界。
- 在独立规则 Slice 批准前，不得自动恢复 HP、法术位、职业资源，不得自动推进控制期限或重选武器精通。
- 后续规则 Slice 必须逐项定义来源、状态变化、覆写、事件和失败处理。

## BL-034 武器精通目录、资格展示与战斗触发候选

### 来源与阶段

本项从 BL-018/v0.3.0 M1-S5 已实现骨架中抽出，并与 BL-021 的效果候选、BL-022 的完整职业资格保持连接。

1. **目录与资格阶段：** 建立可扩展且来源已准入的武器/精通词条目录；角色卡展示资格来源、可选数量、当前选择、未知项和 DM 覆写。
2. **战斗触发阶段：** 在命中、伤害、目标等必要事实由 DM 确认后生成候选；DM 接受或拒绝，应用时写入事件并防止重复触发。

当前 Vex 窄候选与其余人工处理只是基础证明，不代表完整武器精通已经实现。长休重选属于 BL-033 的 AdventureState/休息入口；完整全职业资格仍属于 BL-022。首版不建设自动攻击、自动命中或完整规则执行器。

## BL-035 本地恢复点、刷新后一步撤销与灾备

### 来源与目标

本项从 BL-016、BL-017 和 BL-009 共同暴露的数据安全问题中抽出，避免把本地恢复能力埋进未来多人服务。它不替代当前自动保存，而是在当前会话之外增加独立恢复层。

### 本地阶段

- 保存经过验证、带时间戳的滚动恢复点，与 current session 分开存放。
- 恢复时永不覆盖或删除损坏来源；先展示来源、时间和校验结果，再由 DM 选择恢复。
- 只持久化最近一个可逆操作的 checkpoint，使刷新后可以撤销最后一步；不把每个事件的完整 before/after 快照长期塞入 `localStorage`。
- 明确恢复点数量、轮换、浏览器容量、Schema、旧键只读、导出和损坏数据保留合同。
- 骰子等不可重演随机事件仍不得通过撤销重新掷取结果。

### 服务端延伸

进入 BL-009/BL-017 后，扩展为持久事件历史、版本化存储、备份与恢复演练。服务端灾备不能反向削弱本地数据损坏保护、幂等或补偿事件语义。

## BL-036 可逆变身与战时形态状态机

### 来源与边界

本项连接 BL-033 的 AdventureState 与 BL-008 的空间几何，但不并入任何一方。它处理野性变身、变形术等可逆、可能跨战斗持续的形态；永久新身体继续属于 CharacterProfile，死亡后对象转化继续使用 BL-020/v0.5-v0.6 的独立后继身份。

### 候选模型与流程

- `AdventureState.activeForm` 保存可为空的 `FormInstance`：来源、形态身份、开始/到期、可否主动解除、独立形态 HP/资源和原形状态引用。
- 同一参战者在变身期间保留 CombatantInstance 身份、阵营、先攻槽位、位置和事件历史；CombatProjection 改为展示当前 active form。
- 每次启动变身创建新的 FormInstance；主动解除后再次变身不能覆盖上一段历史。
- 建立 `form.activated`、`form.dismissed`、`form.broken` 或等价受控事件；形态 HP 归零时强制解除，溢出伤害必须由后续明确规则 Slice 或 DM 裁定处理。
- 战斗结束时，未解除且仍在持续时间内的形态回写 AdventureState；不能自动在战后消失。

### footprint 与地图

- 变身可将 `1×1` footprint 改为 `2×2 / 3×3`；提交前由 BL-008 的纯几何接口校验稳定锚点、地图边界、占用格和冲突。
- 无明确合法位置时只展示冲突和候选落点，要求 DM 选择；不自动挤开单位或裁定挤压规则。
- 解除时明确记录原形最终落在哪一格，避免同步、恢复和撤销后位置漂移。

本项为常规优先级。具体德鲁伊、变形术、溢出伤害和特殊形态规则按后续 Rule Slice 逐项准入，不在一个版本内建设完整变身规则引擎。

## BL-037 复合骰式优劣势与 DM 全骰式模式

### 候选能力

- **标准 D20 优势/劣势：** 允许 `1d20 + 1d4 + 2` 等复合检定；只对明确的正向 `1d20` 掷两次取高/低，其他骰项正常结算。存在多个可能的主 d20 时不得静默选择。
- **DM 自定义全骰式模式：** 每颗骰子掷两次，并按“对最终总值有利/不利”选择。对总值有利时，正骰项取高、负骰项取低；不利时相反。例如 `1d20 + 5 - 1d4` 不会因“取高”反而扣除更多。
- UI 和事件必须把第二种模式明确标为 DM 自定义，不冒充 D&D 标准优势/劣势。
- 事件保存模式、每颗骰子的原始结果对、保留值、项符号和最终总值，恢复时不重掷。

本项为常规优先级，只增强本地骰式计算与审计。服务器公平随机仍属于 BL-011；玩家权限和效果触发仍属于 BL-021；本项不得自动判断检定合法性、命中、伤害或资源消耗。

Backlog 项只能通过新的或经重新批准的 ABC 进入 Implementation。
