## 先读这一页：你不需要逐行读代码

你当前最需要掌握的，不是 JavaScript 语法，而是每一项功能回答下面五个问题：

1. 用户想完成什么事？
2. 哪份数据才是这件事的事实来源？
3. 哪个模块可以修改它？
4. 系统如何记录、保存和恢复这次修改？
5. 哪些判断仍必须由 DM 完成？

只要能回答这五个问题，你就能判断一个新需求应该放在哪里、它会不会伤到旧功能、以及是否值得拆成一个版本。

## 1. 产品的边界：它是什么，不是什么

`DND Terminal` 是给 DM 使用的本地跑团战斗辅助工具。它帮助你保存、展示、计算候选、记录裁定和复盘战斗。

它目前不是：

- 完整 VTT；
- 完整 D&D 规则引擎；
- 玩家可直接共同编辑的在线系统；
- 云端服务或正式部署产品。

这不是“功能不够”，而是明确的产品取舍：系统应当减少 DM 的机械负担，但不能在规则来源不足时伪装成自动裁判。

## 2. 一张总图：数据从哪里来，最后到哪里去

```text
长期模板 / 长期角色
UnitTemplate / CharacterSheet
          │
          ▼
遭遇准备：谁参战、初始位置、先攻
EncounterMember
          │
          ▼
战斗前冻结角色数据
CombatProjection
          │
          ▼
本场独立单位
CombatantInstance
          │
          ▼
用户操作 → Command → CombatEvent → CombatSession Snapshot
          │                         │
          │                         ├─ localStorage 自动保存 / JSON 导出
          │                         └─ 日志、撤销、未来灾备与多人同步基础
          ▼
Status Projection → 七个工作区 / 面板 / UI 偏好
```

最重要的一句话：

> **同一个角色、模板、战斗单位和页面显示，不是同一份数据。**

把它们混成一张“大对象”，短期写得快，长期一定失控。现在项目已经建立了基本隔离，这正是它能够继续演进的原因。

### 3.1 战斗操作、事件与保存

典型路径：

```text
DM 点击“扣血”
→ command() 先取得可撤销快照
→ 修改 CombatSession 中的本场 CombatantInstance
→ emit() 写入 CombatEvent
→ localStorage 保存精简后的会话
→ render() 重新绘制页面
```

这不是“多绕一圈”，而是为了让系统能够回答：谁在何时改了什么、为什么改、能否撤销、刷新后还能否恢复。

当前撤销依赖内存中的操作前快照；刷新后不能撤销，是现有边界，不是误操作。未来若做“刷新后撤销一步”，应与本地灾备一起设计，而不是把所有快照无限塞进浏览器存储。

### 3.2 遭遇、先攻、地图与单位

单位流转要这样理解：

```text
UnitTemplate
  = 长期模板，例如地精、NPC 或自定义怪物
        ↓
EncounterMember
  = 本次遭遇的准备成员，可摆放、设为预备、确认先攻
        ↓
CombatantInstance
  = 已开战后的独立棋子；HP、位置、资源、状态只属于本场
```

第 0 回合的作用是把“准备”与“事实已开始”分开。未确认前，可以调整摆放和参战名单；确认后，才生成正式战斗实例和事件。

当前地图已经能处理二维方格、矩形 footprint、边界、棋子重叠、范围模板和基础移动距离。它还不能自动处理墙、视线、掩护、复杂碰撞、推拉或地形；这些都应作为未来几何能力逐步加入。

### 3.3 长期角色、导入、投影与战后回写

角色功能是当前复杂度最高的业务区。请记住这条链：

```text
CharacterRecord
  └─ CharacterSheet revision N
        ↓
   CombatProjection（冻结本次参战所需数据）
        ↓
   EncounterMember
        ↓
   CombatantInstance
        ↓
   PostCombatDiff（战后候选差异）
        ↓ DM 逐项确认
CharacterSheet revision N+1
```

这里写的是当前已经实现的数据链。Backlog 中的 `CharacterProfile → AdventureState → CombatantInstance` 是 BL-033 的未来架构方向，目前尚未实施，不能用未来命名反向解释当前存量数据。

为什么不直接把战斗结果写回角色卡？因为一场战斗可能中途被修正、长期角色也可能被另一处编辑。当前系统宁愿把差异标为过期，也不偷偷覆盖长期资料。

Excel 导入也遵循同样思想：固定 Profile 只生成 `CharacterDraft`，先展示映射、缺失和冲突；DM 确认后才创建正式角色修订。它目前不做模糊自动识别，也不使用 AI 自动补齐规则。

### 3.4 PC 生命周期

PC 和怪物的“0 HP”不是同一件事。

- 怪物/NPC：当前主要由 DM 记录死亡或特殊结果。
- PC：有 `active / dying / stable / dead / needs-review` 等生命阶段；死亡豁免、稳定、倒地与起立均有独立处理。
- 死亡后：可以恢复原身体、以新的永久身体/形态继续，或产生独立受控不死生物。

注意：当前 `lifeStatus: transformed` 是死亡后对象拓扑的历史语义，**不是**德鲁伊野性变身。当前版本没有可逆变身能力；任何后续实现都不能复用这个字段。

### 3.5 骰子、范围与效果

骰子模块负责“已经掷出了什么”，而不是自动裁定“是否命中”。骰果会作为 `dice.rolled` 事件保存；恢复时不会重新随机。

范围模块负责“哪些格、哪些单位可能受影响”：

```text
拖动范围
→ geometry 按 50% 格子覆盖给候选格
→ 自动列出候选单位
→ DM 手动增加或移除目标
→ 确认伤害、治疗、Buff 或状态
→ 写入 range.applied 事件
```

因此，`geometry` 的职责是空间计算与解释，不是完整规则裁判。体型变化、推拉、传送、墙体和地形尚未实现，均由现有 Backlog 单独管理。

### 3.6 工作台、面板与状态投影

v0.7 将界面拆成战斗、地图、角色、单位库、日志、掷骰、设置七个工作区。

`Status Projection` 是只读摘要层。它将散落在战斗对象上的 HP、生命状态、在场状态、回合、效果、待回写等信息整理成“当前行动者”“阻塞项”“待 DM 处理事项”等易读信息。

`Panel Registry` 则记录每个面板属于哪里、负责什么、能否隐藏、默认顺序与宽度。布局只有三档宽度，核心面板不可隐藏，并有一键重置。这是一种有意的受控自由，而不是做一个自由拖拽桌面。

v0.7.1 在此基础上固定左侧 20% 的工作台比例，并按全量、战斗、死亡处理分配地图与检视空间；窄屏退化为纵向任务流。`src/workbench-foundation.css` 是这层布局的统一入口，`src/map-controller.js` 负责地图提示条平移、键盘平移和空白视图切换。平移和导航属于展示状态，不写入战斗事实；棋子移动仍沿原有 Command/Event 路径提交。

## 5. 前端术语白话表

| 术语 | 白话解释 | 本项目里的例子 |
| --- | --- | --- |
| Module（模块） | 按职责拆开的代码文件 | `dice.js` 只负责骰式解析与掷骰 |
| ES Module | 浏览器通过 `import` 把模块拼起来的方式 | `app.js` 导入 `geometry.js` |
| State（状态） | 此刻系统记住的事实 | 本场谁在第几格、还有多少 HP |
| Render（渲染） | 根据状态重新画出页面 | 操作完成后 `render()` 更新页面 |
| DOM | 浏览器里真实存在的按钮、表单、卡片 | `querySelector()` 找到某个按钮 |
| Event（事件） | 一条已经发生、可追溯的业务记录 | `dice.rolled`、`range.applied` |
| Command（命令） | 用户提出的、尚待系统执行的操作请求 | “对某单位扣 8 HP” |
| Snapshot（快照） | 某个时刻状态的完整照片 | 用于快速恢复与当前撤销 |
| Projection（投影） | 从事实算出的只读展示摘要 | 工作台里的“待 DM 复核” |
| Schema（结构版本） | 数据有哪些字段、如何解释的合同 | 不同 Session Envelope 版本 |
| Migration（迁移） | 让旧数据安全适配新结构 | 新 storage key 读取旧 key 后复制写入 |
| Copy-on-write | 不改写旧数据；验证后写入新位置 | v0.7 读取旧会话但只写新 key |
| localStorage | 浏览器给网页的一小块本地存储 | 当前会话、角色库、UI 偏好 |
| Pure function（纯函数） | 输入相同，输出必相同；不偷偷改外部状态 | `geometry` 适合提供此类计算 |
| State machine（状态机） | 对象只能按允许路线切换状态 | PC 正常 → 濒死 → 稳定/死亡 |

## 6. `app.js` 为什么大，以及正确的瘦身方式

`src/app.js` 目前既做页面渲染、DOM 绑定，又处理许多业务编排、事件、保存和跨模块协调，因此显得过大。这是早期快速建立最小闭环的自然结果，不代表当前项目失败。

它会带来三个真实风险：

1. 改一个功能时很难判断会影响哪些页面和状态；
2. 重复逻辑容易残留，例如旧的 `startInitiative()` 实现；
3. 新功能继续堆进去后，任何人都更难定位职责。

但现在不适合“大重写”。正确方向是渐进式瘦身：

```text
app.js
  保留：用户意图、统一 Command、事件、保存、重绘、跨模块协调

encounter/
  承担：摆放、先攻、移动、投入、离场、再入场、参战生命周期

characters/
  承担：角色修订、投影、战后差异、回写审核

geometry/
  承担：占格、距离、范围、未来的位移候选

workbench/
  承担：Projection、工作区、布局偏好
```

`encounter` 也不能变成下一个 `app.js`。它应继续拆成先攻、摆放、移动、参与关系等小模块；PC 生死逻辑仍单独留在 lifecycle 模块。

## 7. 哪些地方适合改，哪些地方先不要碰

### 相对安全的改动

- 文案、标签、卡片层级和 CSS 视觉调整；
- 新增只读信息展示；
- 受控的工作区面板调整；
- 骰式解析的独立小功能，并配套单元测试；
- 不改变旧字段含义的纯计算函数。

### 需要先做设计再动手的改动

- `app.js` 中跨模块流程；
- 任意 `localStorage` key、Session Schema 或迁移逻辑；
- `CombatEvent` 的语义、撤销与补偿逻辑；
- CharacterSheet 修订、战后回写、角色身份；
- 地图坐标、footprint、位置与几何计算；
- 玩家权限、多人同步、服务端 Authority；
- 可逆变身、长短休、资源重置等跨战斗状态。

### 一个很实用的改动前检查

每次准备实施前，先问：

```text
这是展示变化，还是业务事实变化？
它是否需要新事件？
它刷新后是否必须保留？
它影响长期角色、单场战斗，还是仅影响 UI？
旧存储如何读取与回退？
它是否需要 DM 确认，而不应自动执行？
```

只要其中两项以上回答“是”，就应该先做一个小型设计/ABC，而不是直接修改代码。

## 8. 推荐的学习路线

不要从 `app.js` 第一行开始读。建议按这个顺序理解：

1. **先跑一场最小战斗。** 观察“模板 → 遭遇 → 战斗实例 → 事件日志”。
2. **在日志里看一次扣血和撤销。** 理解“事件”和“快照”的区别。
3. **创建或导入一个角色。** 再看它如何投影到遭遇、如何生成战后候选差异。
4. **看一次范围预览。** 理解“候选”与“DM 确认”的产品边界。
5. **切换工作区和布局。** 理解 UI 偏好为何与战斗事实隔离。
6. **最后才打开源码。** 每次只从一个函数出发：它读取什么、修改什么、写了什么事件、谁调用它。

建议的代码阅读入口：

```text
src/dice.js                 最小、最容易建立信心
src/geometry.js             纯计算，较少 UI 干扰
src/encounter.js            单位与战斗对象的转换
src/characters.js           角色卡与回写的业务核心
src/session-persistence.js  保存时哪些东西会被保留
src/workbench-v070.js       前端工作台的清晰边界
src/app.js                  最后阅读：它负责把所有模块接起来
```

## 9. 作为项目负责人，你现在已经能做的判断

你不必能亲手写出每个函数，但你已经应该能够判断：

- 需求属于长期角色、战斗实例、地图几何，还是纯 UI；
- 某个功能是否会跨越多个 Authority；
- 一次“方便的小改动”是否实际上涉及 Schema、事件或迁移；
- 是否需要先定义 DM 确认点；
- 是否应先做底层架构，再做表面功能；
- 是否应该把需求放入 Backlog，而不是立即实施。

这就是对项目的控制权。工程能力不是“记得所有代码”，而是知道该让谁负责、该在哪里改、该先问什么，以及什么时候应该停下来先设计。

## 10. 每次新交付立项前的固定提问模板

可以直接复制下面这段作为未来讨论的开场：

> 这个需求的用户目标是什么？它属于长期资料、冒险状态、单场战斗、地图几何、事件记录，还是 UI 偏好？谁有最终确认权？它会产生什么事件和持久化数据？旧数据如何兼容？哪些规则必须保持为 DM 裁定？它是小修复、独立 Slice，还是应该先进入 Backlog？

正式开始新交付方向讨论时，Agent 还必须按 `AGENTS.md` 的 Pre-Delivery Direction Review 读取当前 Authority、P1 Backlog 和依赖，给出两至三个候选方向及一个明确推荐；本模板不能替代该门禁。
